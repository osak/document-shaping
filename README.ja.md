# Document Shaping

[English](README.md)

Document Shaping は、設計書などの正式な文書や、明示的に依頼された技術文書を、読み手が必要とする情報に合わせて構成するための AI エージェント向けスキルです。何を先に伝え、どこを詳しく説明し、何を要約・参照・省略するかを考えます。

## 使いどころ

設計書、仕様書、アーキテクチャ決定記録（ADR）、実装計画、レビュー資料、継続的に参照するドキュメントの作成や改訂を依頼するときに使えます。読み手を意識したコードコメントや、背景を含む技術解説にも使えます。

## スキルの動作

読者が持つ前提知識、作業の経緯をどこまで共有しているか、どれくらい時間を置いて読むか、読者の目的、文書を使い続ける期間を踏まえて、何を先に示し、どこまで背景を補うかを決めます。概念は読者に通じる用語で説明し、コードの特定・変更・検証に必要な箇所では、実装上の正確な名前を示します。

一部の改訂では、周囲の構成を保ちながら依頼された箇所を整えます。新規作成や大幅な改訂では、情報を整理し、文書全体の構成を読者の視点で見直します。執筆時の指示は、その指示自体が文書の題材である場合を除き、成果物には含めません。依頼に応じて、構成を決めた理由も説明します。

## エージェントで使う

エージェントのスキルディレクトリに `document-shaping` という名前でクローンします。Claude Code なら次のとおりです。

```sh
git clone https://github.com/osak/document-shaping.git ~/.claude/skills/document-shaping
```

あとは `/document-shaping` に続けて、どんな文書がほしいかと、誰が読むかを書くだけです。スキルに対応していないエージェントでは、`document-shaping/SKILL.md を読んで、〜` のように SKILL.md を読ませてから頼んでください。

### 読み手を伝える

ペルソナとは、できあがった文書を誰がどう使うかを表した読者像です。「読者は〜」の形で、その人の役割、すでに知っていること、読んだあとに何をするかを伝えてください。読む時期によって残すべき情報が変わるなら、それも書いておくと効きます。一部だけ直したいときは、対象の節も指定してください。

「読者はバックエンドエンジニア」の一言でも、技術レベルの目安になります。「読者は既存のキューには詳しいけど、提案の議論には出ていなかったバックエンドエンジニア。次の設計レビューで再試行方式の変更を承認するか決める」まで書けば、どの背景を補って、どの判断材料を先に出すべきかまで伝わります。

### 依頼の例

ざっくり頼んでも、細かく指定しても動きます。短い依頼ならエージェントが文書の種類や依頼内容から読者像を補い、詳しく書くほど意図に沿った構成になります。

#### レビュー向けの設計書

ざっくり頼む場合:

```text
/document-shaping 添付のメモから設計書を書いて。読むのは設計レビューの参加者。
```

詳しく頼む場合:

```text
/document-shaping 添付したキューの再試行のメモから、次の設計レビュー用の設計書を書いて。
読者は既存のキューには詳しいけど、提案の議論には出ていなかったバックエンドエンジニア。レビューでこの変更を承認するか決める人たち。
今の再試行で何が困るのかを先に軽くまとめて、重複処理・障害からの復旧・切り替えのリスクあたりで提案と代替案を比べてほしい。承認に関わりそうな未決事項があれば、それも出しておいて。
```

#### 将来の保守担当者向けの部分改訂

ざっくり頼む場合:

```text
/document-shaping 決定メモをもとに、運用ガイドの「再試行ポリシー」節を直して。読むのは将来の運用担当者。
```

詳しく頼む場合:

```text
/document-shaping 添付の決定メモをもとに、キューの運用ガイドの「再試行ポリシー」節だけ直して。
読者は数か月後にキューの運用を引き継ぐオンコール担当。キューの仕組み自体はわかっているけど、元の決定メモは見られない前提で。
再試行回数に上限がある理由、上限に達したらどうなるか、上限を変える前に何を確認すればいいかが残っているとうれしい。
```

#### AI エージェント向けの実装計画

ざっくり頼む場合:

```text
/document-shaping 添付の仕様を実装計画にして。読むのはコーディングエージェント。
```

詳しく頼む場合:

```text
/document-shaping 添付したキューの再試行の仕様を実装計画にして。
読者はリポジトリをチェックアウトしたばかりのコーディングエージェント。コードを読んだりテストを回したりはできるけど、このチャットは見られない。計画だけ読めば実装して動作確認までできるようにしたい。
触るファイルや識別子、期待する挙動、異常系、確認の手順を入れて。仕様で決まっていないところは、はっきりそう書いておいて。
```

#### カスタマーサポート向けの切り替えガイド

ざっくり頼む場合:

```text
/document-shaping 添付のリリースメモから、サポートチーム向けのガイドを書いて。
```

詳しく頼む場合:

```text
/document-shaping 添付のリリースメモから、カスタマーサポート向けのガイドを書いて。
読者は製品にも問い合わせ対応の流れにも慣れているサポート担当。切り替え後の最初の一週間、お客さんからの質問に答えるときに使う。
お客さんから見て何が変わるか、サポート側で何を確認できるか、どこでエスカレーションするか、そのとき何を伝えるかがわかるようにしてほしい。
```

## リポジトリの構成

| ファイル | 内容 |
| --- | --- |
| [SKILL.md](SKILL.md) | スキルを適用するエージェント向けの指示一式。 |
| [DESIGN.md](DESIGN.md) | 設計の理由と、スキルを保守・拡張する際の原則。 |
| [LICENSE](LICENSE) | 再配布の条件を含む zlib ライセンス。 |

スキルの動作を変えるときは、`SKILL.md` だけで適用できる状態を保ち、変更の理由を `DESIGN.md` に記録してください。適用範囲を保ったまま、部分改訂と文書全体の作成の両方で意図どおりに機能するか確認してください。
