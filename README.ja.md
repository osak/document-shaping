# Document Shaping

[English](README.md)

Document Shaping は、設計書などの正式な文書や、明示的に依頼された技術文書を、読み手が必要とする情報に合わせて構成するための AI エージェント向けスキルです。何を先に伝え、どこを詳しく説明し、何を要約・参照・省略するかを考えます。

## 使いどころ

設計書、仕様書、アーキテクチャ決定記録（ADR）、実装計画、レビュー資料、継続的に参照するドキュメントの作成や改訂を依頼するときに使えます。読み手を意識したコードコメントや、背景を含む技術解説にも使えます。

## スキルの動作

読者が持つ前提知識、作業の経緯をどこまで共有しているか、どれくらい時間を置いて読むか、読者の目的、文書を使い続ける期間を踏まえて、何を先に示し、どこまで背景を補うかを決めます。概念は読者に通じる用語で説明し、コードの特定・変更・検証に必要な箇所では、実装上の正確な名前を示します。

一部の改訂では、周囲の構成を保ちながら依頼された箇所を整えます。新規作成や大幅な改訂では、情報を整理し、文書全体の構成を読者の視点で見直します。執筆時の指示は、その指示自体が文書の題材である場合を除き、成果物には含めません。依頼に応じて、構成を決めた理由も説明します。

## エージェントで使う

作業場所にリポジトリをクローンします。

```sh
git clone https://github.com/osak/document-shaping.git
```

クローンしたディレクトリの親ディレクトリから、`document-shaping/SKILL.md` を読んで、指定した文書を作成または改訂するようエージェントに依頼します。スキルを自動検出させる場合は、利用するエージェントが対応するスキルディレクトリに、`document-shaping` という名前で配置します。すでにスキルを利用できる場合は、依頼でスキル名を直接指定できます。

### 読者のペルソナを指定する

ここでいうペルソナは、完成した文書を誰がどう使うかを具体化した読者像です。「読者は〜です」と書き、役割、すでに知っていること、読んだあとに判断・実行することを具体的に伝えます。読む時期が残すべき情報に影響するなら、その時期も添えます。元になる資料を渡し、一部だけ改訂する場合は対象の節を指定します。

「読者はバックエンドエンジニアです」と書けば、技術レベルの目安になります。「読者は既存のキューに詳しいものの、提案時の議論には参加していないバックエンドエンジニアです。次の設計レビューで再試行方式の変更を承認するか判断します」と書くと、文書だけで伝えるべき背景や、先に示すべき判断材料まで指定できます。

### レビュー担当者向けの設計書

```text
document-shaping/SKILL.md を読み、添付したキューの再試行に関するメモから、次回のレビューに向けた設計書を書いてください。
読者は既存のキューに詳しいバックエンドエンジニアです。提案時の議論には参加しておらず、レビューで変更を承認するか判断します。
現行の再試行処理で何が問題になるかを要約したうえで、重複処理、障害からの復旧、切り替え時のリスクの観点から提案と代替案を比較してください。承認の判断に影響する未決事項も示してください。
```

### 将来の保守担当者向けの部分改訂

```text
document-shaping/SKILL.md を読み、添付した決定メモをもとに、キューの運用ガイドの「再試行ポリシー」節だけを改訂してください。
読者は数か月後にキューの運用を引き継ぐオンコール担当のエンジニアです。キューの一般的な仕組みは知っていますが、元の決定メモは参照できません。
再試行回数に上限を設けた理由、上限に達したときの挙動、上限を変える前に確認すべきことを記載してください。
```

### AI エージェント向けの実装計画

```text
document-shaping/SKILL.md を読み、添付したキューの再試行仕様を実装計画にしてください。
読者はチェックアウトしたばかりのリポジトリで作業を始めるコーディングエージェントです。コードの確認やテストの実行はできます。このチャットを参照せずに変更を実装し、動作を検証できる計画にしてください。
変更対象のファイルと識別子、必要な挙動、異常系、検証手順を記載してください。仕様で決まっていない点も明示してください。
```

### カスタマーサポート向けの切り替えガイド

```text
document-shaping/SKILL.md を読み、添付したリリースメモをもとにカスタマーサポート向けのガイドを書いてください。
読者は製品と問い合わせ対応の流れを把握しているサポート担当者です。切り替え後の最初の一週間に、顧客からの質問に答えるために使います。
顧客から見て何が変わるか、サポート側で確認できること、どの時点でエスカレーションするか、その際に何を伝えるかを記載してください。
```

## リポジトリの構成

| ファイル | 内容 |
| --- | --- |
| [SKILL.md](SKILL.md) | スキルを適用するエージェント向けの指示一式。 |
| [DESIGN.md](DESIGN.md) | 設計の理由と、スキルを保守・拡張する際の原則。 |
| [LICENSE](LICENSE) | 再配布の条件を含む zlib ライセンス。 |

スキルの動作を変えるときは、`SKILL.md` だけで適用できる状態を保ち、変更の理由を `DESIGN.md` に記録してください。適用範囲を保ったまま、部分改訂と文書全体の作成の両方で意図どおりに機能するか確認してください。
